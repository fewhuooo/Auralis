# 编码、文档与 Git 规范

更新时间：2026-07-10

文档状态：现行

权威范围：代码风格原则、工作树保护、测试证据、分支提交和文档维护规范

事实来源：当前 Vue、Uni-app、Spring Boot 项目结构与仓库协作约束

## 适用范围

本规范适用于 PC、Mobile、Tablet、Server、基础设施和文档修改。模块内部已有更严格约定时，以模块约定为补充，但不得降低本文件的保护要求。

## 工作树保护

- 修改前必须运行 `git status --short`。
- 未明确属于本任务的修改视为用户成果，必须保留。
- 禁止使用破坏性命令清理工作树。
- 暂存时必须使用明确路径，禁止无检查地执行 `git add -A`。
- 提交前必须检查 `git diff --cached --name-status`，确保没有夹带无关文件。

## 先复用现有结构

- 新增代码前必须搜索同类实现、Store、服务、类型、组件和文档。
- 相同职责只能有一个权威实现；禁止为绕开理解成本创建平行版本。
- 删除或移动现有入口前，必须检查路由、导入、文档、构建脚本和用户流程。

## 前端规范

- Vue 组件保持单一职责，复杂状态优先归入现有 Pinia Store 或服务层。
- 页面路由、页面目录、导航组件和文档页面地图必须一致。
- API 调用统一经过现有请求封装；禁止在页面散落新的 base URL、token 或错误处理。
- 跨端功能必须明确 PC、Mobile、Tablet、H5、微信和 Tauri 的适用范围。
- 视觉修改复用 `docs/design/Frontend.md` 的令牌和交互规则。

## 后端规范

- Controller 负责协议边界，Service 负责业务规则，Mapper/Entity 负责持久化映射。
- 所有用户数据访问必须以当前认证用户作为隔离边界。
- 普通受保护 API 禁止接受 refresh token。
- Controller、DTO、Entity、DDL 和文档字段必须同步核对。
- 配置密钥使用环境变量或配置绑定，禁止硬编码生产凭据。

## 文档规范

- 现行 Markdown 必须位于分类目录，`docs/README.md` 除外。
- 每份现行文档必须有四项元数据。
- 当前事实、产品需求、未来计划、历史变化和展示材料必须分开维护。
- 同一事实只在一个权威文档完整描述，其他文档使用摘要和相对链接。
- 修改链接后必须检查目标存在；修改路径后必须全仓搜索旧引用。
- 历史归档正文不得做事实修正。

## 测试与验收证据

- 先定义命令证明什么，再运行命令。
- 失败命令必须保留退出结果和首个可操作错误。
- 没有测试源码时，`mvn test` 通过不能写成业务测试已覆盖。
- Web/H5 构建通过不能替代 Tauri GUI、微信开发者工具、手机或平板真机验收。
- 外部数据库、对象存储、向量库和 AI 提供商未联调时必须明确写出。

## 分支规范

- 功能分支默认使用 `codex/<topic>`。
- 禁止在未获明确许可时直接在 `main` 上开始实现。
- 分支名称使用小写短语和连字符，例如 `codex/docs-reorganization`。

## Commit Message

格式：

```text
<type>(<scope>): <summary>
```

常用 type：`feat`、`fix`、`docs`、`refactor`、`test`、`build`、`chore`。

提交必须满足：

- 一个提交表达一个可独立审查的结果。
- summary 使用祈使语义，不写空泛的 `update files`。
- 文档迁移、代码实现和验证证据可以拆为不同提交。

## 提交检查表

1. `git diff --check -- <任务路径>` 无本任务新增空白错误。
2. 实际验证命令已运行并记录结果。
3. 受影响权威文档已同步。
4. `git diff --cached --name-status` 只包含任务文件。
5. 用户原有无关修改仍存在且未被覆盖。
6. 最终交接列出剩余风险和人工验收。
