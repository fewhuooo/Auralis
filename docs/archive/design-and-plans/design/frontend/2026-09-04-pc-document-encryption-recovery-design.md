# PC 文档处理密钥恢复边界设计

更新时间：2026-11-15

文档状态：已批准，待实施

## 问题

`DocumentProcessingRuntime` 启动时会检查持久化的文档任务。现有实现只要发现
`payloadCacheId` 或 `payloadReceipt`，便把任务视为需要使用既有主密钥恢复的任务。
失败任务或清理失败的成功任务仍可能保留 receipt。因此，当 OS keyring 中没有主密钥
时，这些任务会阻止初始化，导致新的学科文件解析器无法启动。

## 已被替代的阶段筛选方案

早期方案仅检查上传恢复阶段，并忽略终态 receipt。11-15 源码核对确认该方案不适用：
`SourceJobScheduler.retry()` 会保留失败任务的 receipt，将任务转为 `QUEUED`，随后直接
进入 `UPLOADING` 读取旧缓存；`READY` 的清理失败也会保留 receipt。不能仅按阶段白名单
允许初始化新密钥，否则后续仍会用新密钥读取旧密文。以下 10-10 决策为现行实施依据。

## 2026-10-10 产品决策更新（已确认，待实现）

该主密钥只保护 PC 本地文档处理产生的加密 cache/package，不是知识块、任务、账户
或原始文件的通用端到端加密密钥。因此不增加通用密钥备份/恢复入口。

当 OS keyring 明确确认原密钥不存在时，产品目标改为自动初始化新密钥，并废弃受影响
任务的旧加密 cache、receipt 与续传进度；不得尝试用新密钥解密或续传旧密文。随后从
仍可取得的原始文件重新处理并上传；原始文件无法从本地或受管资产恢复时，提示用户
重新选择文件上传。旧 cache 清理及任务检查点重置必须可安全重试，不能让过期 receipt
再次进入旧缓存续传路径。

仅确认 keyring 条目缺失时才执行上述恢复。访问被拒、凭据库不可用等其他 keyring
错误继续报告原始错误，不得视作密钥丢失或静默轮换密钥。当前 `runtime.ts` 仍对带
cache id/receipt 的任务报告 `DOCUMENT_ENCRYPTION_KEY_RECOVERY_REQUIRED`；本节是已确认
的产品决策，代码与 Windows Tauri/真实 Server 验收尚未完成。11-15 核对还确认
`e2ee.isEnabled()` 将 keyring 查询异常转为 `false`；实施时必须保留访问错误与明确缺失
的区别，并覆盖失败重试及 `READY` 清理残留，不能直接采用旧阶段筛选补丁。

## 验证

- 增加行为回归，证明失败任务重试和 `READY` 清理残留均经过旧缓存及续传状态失效化，不会因终态阶段直接放行初始化。
- 增加行为回归，证明确认密钥缺失时不会读取旧 cache，而会废弃旧续传状态并从原始输入重新处理。
- 增加行为回归，证明 keyring 访问错误不会触发密钥轮换。
- 保留现有 native package 初始化边界测试，并运行文档处理定向套件与可用的类型检查。

## 人工验收边界

需在 Windows Tauri 中验证：已有成功任务、keyring 条目不存在时，重新登录后可上传
并解析一个新文件；真实可续传任务的密钥丢失后，旧缓存不会被解密或续传，原始文件
可用时从头重新处理/上传，不可用时提示用户重新选择文件；凭据库访问异常显示真实错误。
