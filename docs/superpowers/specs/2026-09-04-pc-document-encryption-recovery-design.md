# PC 文档处理密钥恢复边界设计

更新时间：2026-09-04

文档状态：已批准，待实施

## 问题

`DocumentProcessingRuntime` 启动时会检查持久化的文档任务。现有实现只要发现
`payloadCacheId` 或 `payloadReceipt`，便把任务视为需要使用既有主密钥恢复的任务。
但成功或已失败的终态任务也会保留 receipt；成功任务的缓存对象已在服务端确认后
清理。因此，当 OS keyring 中没有主密钥时，历史终态任务会错误阻止首次初始化，
导致新的学科文件解析器无法启动。

## 决策

只将同时满足下列条件的任务视为“密钥恢复必需”：

- 任务处于仍会读取既有加密缓存的上传恢复阶段；以及
- 任务保存了 cache id 或 receipt。

终态任务（`READY`、`FAILED_LOCAL`、`FAILED_SERVER`）的历史 receipt 不阻止创建首
次主密钥。实际可续传的缓存仍不得静默重建密钥，必须保留恢复错误，避免用新密钥覆
盖丢失密钥的旧密文。

Rust 的 `document_package_begin` 继续作为新 package 的最后初始化边界；本变更不改
变读取、上传、删除既有 cache 时必须使用原密钥的约束。

## 验证

- 增加行为回归，证明仅终态历史 receipt 时可以初始化。
- 增加行为回归，证明有 receipt 的上传恢复任务仍返回恢复必需错误。
- 保留现有 native package 初始化边界测试，并运行文档处理定向套件与可用的类型检查。

## 人工验收边界

需在 Windows Tauri 中验证：已有成功任务、keyring 条目不存在时，重新登录后可上传
并解析一个新文件；有真实可续传缓存而密钥丢失时，界面仍给出恢复提示且不尝试解密。
